> final V2 correction, 2026-11-08. Builders update the **Status** column as work progresses
> (GOV-002) and regenerate the table whenever specs change.

**Status values (lifecycle):** `DOCUMENTED` (a process rule, checked by reviews) ·
`IMPLEMENTATION_REQUIRED` (specified, not yet built) · `TEST_REQUIRED` (built, acceptance test not
yet passing) · `BROKER_VERIFICATION_REQUIRED` (part of it needs live broker data first) ·
`USER_DECISION_REQUIRED` (cannot be finalised without a D-decision) · `BLOCKED` (cannot proceed) ·
`VERIFIED` (acceptance test passed; evidence = commit + run reference in `docs/STATUS.md`).
**Nothing is VERIFIED today:** documentation is not evidence.

**Pending user decisions column:** the D-decisions and USER_DECISION_REQUIRED parameters a
requirement's *values* depend on. The requirement's behaviour is fully specified; only the numbers
or mode await the user. Fixture values are used in tests until then (RISK-005).

**Criticality:** `CRITICAL` = trading risk, execution, emergency, Guardian, time, cent validation,
security, privacy, LLM isolation, and the security- or honesty-critical API, MCP, UI, data, research and
process items. `CRITICAL` items must be `VERIFIED` before M10 (03 prompt §2).

**Acceptance criterion convention:** `test_<id>` is the test (or test group) that the builder names
after the requirement. Its exact assertion is the requirement text plus the referenced golden
vectors, chaos tests or review checks. M0 maps each to a concrete test in `docs/TEST_PLAN.md`.

**Parameters, triggers and vectors** are traced through their parents: `P-xx` → TRADING_RISK_SPEC §2
(RISK-005/090/091/092); `T1–T27` → RISK-050..053; `GV-xx` → RISK-001..092; `CGV-xx` → CENT-010..032;
threats `TM-xx` → the SEC/PRV/MCP/API IDs in their mitigation column; decisions `D-xx` → the table
below.
